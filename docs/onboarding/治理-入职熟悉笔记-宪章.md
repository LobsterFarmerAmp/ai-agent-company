## 一、治理体系全景（结论先行）

**结论**：公司治理已形成"规则即代码 + 单世界线 + Delegation First + Self-Improvement"四件套闭环，所有运营动作都有显式机制承载，新人入职后真正缺的不是规则，而是**对规则的索引路径和实战校验**。

**关键依据**：
- 规则层：`company-hard-rules.md` 通过 company-guidelines Hook 在 bootstrap 时幂等注入，所有 agent（含 jia-goushi）一致；
- 执行层：5 类公司技能按触发条件路由（dialogue/dispatch/execution/code/reporting），覆盖 90% 工作面；
- 协作层：单世界线 + sessions_send 走 main session，跨 agent 上下文不撕裂；
- 公司 OS：task / meeting / notice / org / inbox 五个独立工具族，承担有状态运营。

## 五、≥3 条建设性优化建议（结论先行）

### 建议 1：把"行数审计"做成人设治理的硬规则

- **问题**：templates/ 规定了每件套目标行数（AGENTS ≤40 / SOUL ≤35 等），但无任何工具自动校验。当前 7 个 agent 都可能不知不觉超限，治理仓库 README 也因此出现"目标行数 vs 实际行数"的偏差。
- **建议**：在 `~/.openclaw/company/ai-agent-company/skills/persona-audit/` 已有审计基础上，新增 **linter 子技能** `persona-audit/lint.md`，定义每文件软/硬阈值；并把"超硬阈值则阻断 task_submit"作为治理岗审核依据（软阈值提醒，硬阈值阻塞）。
- **预期收益**：人设文件长期保持精炼；新人入职"5 件套填写指引"从口头变可执行；治理岗有量化抓手而非靠经验。

### 建议 2：补一条"规则与文档同步"硬规则，闭合双线维护

- **问题**：`docs/maintenance.md` 明确"运行环境改进必须先回写仓库、再同步部署"，但 `company-hard-rules.md` 第八节只要求"规则改一处 + 公告同步"，未把 `setup/` ↔ `bootstrap/` ↔ `docs/` 三者的双线维护上升为公司规则。已有教训（setup/ 与 bootstrap/ 早期分工模糊）但未固化为规则。
- **建议**：在 company-hard-rules.md 新增第九节 "**双线维护铁律**"——
  - (a) 改 Gateway/Agent/Skill/Hook/Cron 任一运行时配置，必须同步 `setup/` 对应文档，并在同一 commit 引用；
  - (b) 改 `docs/` 治理文档，若影响部署步骤，必须同步 `setup/README.md` 引用；
  - (c) 治理岗（我）每周抽查一次 commit 历史，违规条目入"治理简报"公告。
- **预期收益**：把分散在 MEMORY.md / maintenance.md 的隐性约束显性化；新人无需猜哪里要同步；架构师和我有共同标尺。

### 建议 3：把"端到端真环境验证"加进 Valid Proof

- **问题**：卡路里高工会议已实证 `.env` 占位符导致生产 API 401，但 `pnpm test` 全绿——根因是单元测试不接真实 provider。Valid Proof 三要素（代码可查 / 测试全绿 / 功能真实）中的"功能真实"目前缺乏可观测的硬指标。
- **建议**：把 Valid Proof 升级为四要素——
  1. 代码在 main/指定分支，commit hash 可查（已有）；
  2. root `pnpm test` 退出码 0（已有）；
  3. **新增**：端到端 smoke test（API server 实际启动 + 关键路由真实调用一次）有日志证据；
  4. 功能真实可用（非 mock / 非 dummy key，证据是真实跑通的命令输出）。
  
  并在 `company-task-execution` SKILL.md 的"完成前检查"段落同步加一条："涉及外部 API / 数据库 / 第三方服务时，必须附 smoke test 证据"。
- **预期收益**：把"测试绿 ≠ 可用"的盲区制度化填掉；避免再次出现 `.env` 占位符这种低级却阻塞业务的故障；治理岗 review 时多一项硬证据。

### 建议 4（备选）：治理岗新增"每周公告合规心跳"

- **问题**：当前 HEARTBEAT.md 是空模板，治理岗没有任何自动任务，规则变更是否伴随公告、是否有人 read 全靠人肉。
- **建议**：治理岗 HEARTBEAT.md 写入两条周心跳：
  - 每周一次扫 `~/.openclaw/company-info/company-hard-rules.md` 最近 git log，对照 `company_notice_list` 看每次规则修改是否伴随公告；
  - 每周一次扫各 agent workspace 的 5 件套实际行数，违反硬阈值的发 `company_task_revise`（如可行）。
- **预期收益**：治理从"被动响应"转"主动巡查"；和 CTO 拆解 + Boss 决策形成第三道防线。
